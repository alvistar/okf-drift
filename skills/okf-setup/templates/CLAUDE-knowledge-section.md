## Knowledge Bundle
Project knowledge lives in `knowledge/` as an Open Knowledge Format (OKF v0.2) bundle: `project/` (state, stack, setup, conventions), `architecture/`, `decisions/` (one concept per decision), `playbooks/` (one per recurring task). Search it with the model-invocable `okf-drift:okf-runtime` skill in recall mode with "<terms>" — never bare `okf search`: recall joins the search with `drift check` and marks STALE any concept whose bound code has changed since it was written, naming the commit to blame. A STALE hit is a lead, not a fact: read the code it points at before relying on it, and quote it only for what the code confirms. A recall that warns `drift did not run` checked nothing. Before editing a specific file, `okf search --for-path <file>` (no drift join — check the hit's `last_updated` against `git log` before trusting it). The bundle has no code graph: use Grep, Glob and LSP for callers and source navigation. The format for a new playbook or decision is at the top of `knowledge/playbooks/index.md` and `knowledge/decisions/index.md` — search will not find it, read the index. The same pinned gate runs through a standalone bootstrap in CI (`.github/workflows/knowledge.yml`) on every PR and on push to `main`: a code change can make a concept stale without touching `knowledge/`, and a stale concept blocks the merge until it is re-stamped via `/okf-write`. Listing `knowledge/` as out of scope for a task hides the gate's cost until CI; it never avoids it.

Recall answers one question: *what is WRITTEN about this area, and what was observed about it?* Use it before asserting anything about the architecture or a decision in a plan, a PR body or a review, and before editing a file a concept governs (`okf search --for-path <file>`, then `git status` and `git log` on that file — the hit's `last_updated` cannot see an uncommitted edit). To find code — a symbol, a caller, a string — use Grep and LSP; recall does not index code.

The runtime skill resolves its launcher from the skill directory supplied by the host and uses this repository's `.okf-drift-version`; no consumer scripts or saved plugin-cache paths are needed. If the skill is unavailable, stop and report the missing plugin; use the pinned bootstrap documented in okf-drift's README (the `pinned runtime gate` step in `.github/workflows/knowledge.yml`). Historical operational commands in `knowledge/` are non-authoritative: this section governs gate and recall. Preserve this project's required read order.

## Work Loop
1. **Context** — read `knowledge/project/state.md`, and if the branch is behind `origin/main`, also `git diff $(git merge-base HEAD origin/main) origin/main -- knowledge/project/state.md`, since a branch's snapshot is as old as its merge-base; open `knowledge/project/state-evidence.md` only for the items the task touches; invoke the model-invocable `okf-drift:okf-runtime` skill in recall mode with "<terms>"; check `knowledge/playbooks/index.md` for a matching playbook and follow it; run `drift check --changed <path> --format json` for every path you plan to touch and report the concepts it names as candidates that may alarm, plus every planned path no concept covers; run the gate once as a baseline and keep its output, because an alarm already present then is inherited, not yours.
2. **Build** — if you deviate from a playbook or a convention, say so before writing code.
3. **Verify** — run the Verify Checklist in `knowledge/project/conventions.md` item by item — the knowledge gate is its first item — before presenting code.
4. **Grow** — after meaningful work: if what works / is missing / is broken changed, update its one line in `state.md` and its entry in `state-evidence.md`; fix any concept that is now wrong; write a decision or a playbook if one was made or one would have saved a wrong turn; bind every new **code** `code_refs` entry with the drift bootstrap; never bind a high-churn file — build/run scripts, CI workflows, `VERSION`, manifests: list it in `code_refs`, give the concept a `stale_after`, and write a claim whose truth lives there as a dated observation; when the gate flags drift, run `okf-restamp.sh --format-only` first (it settles, with one log line, a C/Swift-style file whose lines changed only in indentation), then read each remaining anchor and either fix the concept or run `okf-restamp.sh <doc> <anchor> "<what you read>"`, which re-stamps and writes the log line — never re-stamp code you did not read; run `okf-tidy.sh` for index rows and `last_updated`, and bump `stale_after` yourself only on a concept you reviewed; these helpers run through `/okf-write`'s pinned launcher; run `okf-drift:okf-runtime` in gate mode before pushing — CI runs the same gate on the PR, and a FAIL found there costs a round trip.

## Navigation
At the start of every session, follow the project's required read order first, then read `knowledge/index.md` and `knowledge/project/state.md` (the one-line snapshot) before implementation. Open `knowledge/project/state-evidence.md` only for the items the task touches, never whole.
