## Knowledge Bundle
Project knowledge lives in `knowledge/` as an Open Knowledge Format (OKF v0.2) bundle: `project/` (state, stack, setup, conventions), `architecture/`, `decisions/` (one concept per decision), `playbooks/` (one per recurring task). The code is the source of truth; the bundle holds what the code does not say: why, invariants, traps, conventions, how to behave, and where to look (`code_refs`). Search it with the model-invocable `okf-drift:okf-runtime` skill in recall mode with "<terms>", never bare `okf search`: recall prints each hit's `status · review` and, when commits touched the concept's `code_refs` after the concept's last commit, a change hint naming the count and the last commit. A change hint is a pointer, not a verdict: it says which code to read before you rely on the concept. Before editing a specific file, `okf search --for-path <file>` lists the concepts that govern it (no change hint there; `git log` on the file gives the same lead). The bundle has no code graph: use Grep, Glob and LSP for callers and source navigation. The format for a new playbook or decision is at the top of `knowledge/playbooks/index.md` and `knowledge/decisions/index.md`; search will not find it, read the index.

Read-repair: when a concept you rely on contradicts the code, the code wins. If this session writes the repository, fix the concept with an ordinary `/okf-write` edit; otherwise say so in your answer. A concept you only saw listed in results needs nothing.

Recall answers one question: *what is WRITTEN about this area, and what was observed about it?* Use it before asserting anything about the architecture or a decision in a plan, a PR body or a review, and before editing a file a concept governs. To find code (a symbol, a caller, a string), use Grep and LSP; recall does not index code.

The same pinned gate runs through a standalone bootstrap in CI (`.github/workflows/knowledge.yml`) on every PR and on push to `main`. It checks the bundle's structure, its indexes, dead `code_refs` and expired `stale_after` dates, and it fails while a `drift.lock` exists (drift is no longer used; run `/okf-migrate`). `knowledge/log.md` is the frozen log: the gate fails any change to it. Each branch writes one log entry, `knowledge/log/<YYYY-MM-DD>-<slug>-<4 hex>/log.md`, and only through `okf-log.sh add`, so parallel PRs never conflict on the log.

The runtime skill resolves its launcher from the skill directory supplied by the host and uses this repository's `.okf-drift-version`; no consumer scripts or saved plugin-cache paths are needed. If the skill is unavailable, stop and report the missing plugin; use the pinned bootstrap documented in okf-drift's README (the `pinned runtime gate` step in `.github/workflows/knowledge.yml`). Historical operational commands in `knowledge/` are non-authoritative: this section governs gate and recall. Preserve this project's required read order.

## Work Loop
1. **Context**: read `knowledge/project/state.md`, and if the branch is behind `origin/main`, also `git diff $(git merge-base HEAD origin/main) origin/main -- knowledge/project/state.md`, since a branch's snapshot is as old as its merge-base; open `knowledge/project/state-evidence.md` only for the items the task touches; invoke the model-invocable `okf-drift:okf-runtime` skill in recall mode with "<terms>" and read the code behind every change hint on a concept you will rely on; check `knowledge/playbooks/index.md` for a matching playbook and follow it; run the gate once as a baseline and keep its output, because a failure already present then is inherited, not yours.
2. **Build**: if you deviate from a playbook or a convention, say so before writing code.
3. **Verify**: run the Verify Checklist in `knowledge/project/conventions.md` item by item, the knowledge gate first, before presenting code.
4. **Grow**: after meaningful work, through `/okf-write` and its pinned launcher: if what works / is missing / is broken changed, update its one line in `state.md` and its entry in `state-evidence.md`; read-repair any concept the work proved wrong; write a decision or a playbook if one was made or one would have saved a wrong turn. Write every concept to the writing rule: it holds why, invariants, traps, conventions, how to behave and where to look (`code_refs`), never what the code already says (signatures, defaults, step lists, numbers, field lists); a fact that must be quoted from the code is a dated observation. Log each bundle change with `okf-log.sh add knowledge '<line>'`; run `okf-tidy.sh` for index rows and `last_updated`, and move `stale_after` yourself only on a concept you reviewed; run `okf-drift:okf-runtime` in gate mode before pushing, because CI runs the same gate on the PR and a FAIL found there costs a round trip.

## Navigation
At the start of every session, follow the project's required read order first, then read `knowledge/index.md` and `knowledge/project/state.md` (the one-line snapshot) before implementation. Open `knowledge/project/state-evidence.md` only for the items the task touches, never whole.
